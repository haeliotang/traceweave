# 双语与文案策略（2026-10-31）

这份文档说明：什么文案必须进 `T` 目录，什么可以留在代码里。争议在这里一次讲清，后面不再反复。

## 1. 必须进 `T` 的

- 用户能看到的任何文字：按钮、标题、提示、Toast、对话框正文、空态、徽章、通知正文；
- 会写进用户数据、之后被用户读到的模板：记忆正文、报告段落、归档说明。

理由：`T` 缺任一侧会直接抛错，能把“漏翻译”变成构建期问题，而不是上线后才发现。

## 2. 可以留在代码里的（附理由）

| 类别 | 例子 | 为什么 |
|---|---|---|
| 输入关键词表 | `"便笺","笔记","note","memo"` | 用来匹配用户输入；翻译后就认不出中文输入 |
| 生成内容的匹配串 | `title.contains("日程")` | 判断已有文本属于哪一类，属于解析而非展示 |
| 标识与常量 | `"demo.note.read"`、`"system"` | 不是给人读的文案 |
| 模型提示词 | `LocalSlmEngine` 的指令文本 | 属于模型输入，语言应与输出语言策略一致，而不是跟随界面 |
| 日志 | `Log.i("AgentOsPairing", …)` | 只给开发者看 |

## 3. 现状（基线）

`test_no_new_hardcoded_strings.py` 冻结了当前每文件的含中文硬编码字面量数量：

```
测试 / 模型 / 解析 / 日志类：22 个文件、共 80 处
```

其中 `MainActivity` 只剩 15 处，全部是生成内容的匹配串；`CapabilityBroker` 9 处是能力描述与异常消息（描述同时进入模型提示，异常缺少语言上下文），属于有意保留。

规则：**任何文件不得比基线多，也不得出现新的文件**。要降基线，就迁移或删除；要加文案，就进 `T`。

## 4. 已知的两类“暂时保留”

1. **能力描述**（`CapabilityBroker`）：同时被界面列表和模型提示使用。彻底双语需要把描述改成“键 + 参数”的结构，属于数据模型改动。
2. **异常消息**（`SecurityException`、部分 `IOException`）：由非 UI 层抛出，没有语言上下文。正确做法是异常携带键，界面层翻译。

这两类都已在基线与本文档中记录，不算遗漏。

## 5. 检查方式

```bash
# 目录键是否齐全（代码用到但目录没有）
python3 -m unittest agent_os.tests.test_string_keys
# 是否新增中文硬编码
python3 -m unittest agent_os.tests.test_no_new_hardcoded_strings
# 目录本身是否成对
python3 -m unittest agent_os.tests.test_t_strings
```
