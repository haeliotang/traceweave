## A. 安全与信任模型

### 🔴 A1. 第三方 Agent 的信任模型

**问题**：`SubstrateService` 现在要求 `BIND_SUBSTRATE`（dangerous，用户授权）。但这等于"任何应用只要用户点一次允许，就能注册 agent 并创建任务"。

**选项**
1. **保持现状**：用户授权一次 + 每次能力请求再单独批准（当前实现）。
2. **签名白名单**：只允许与主应用同签名的包绑定（demo agent 打成同签名变体）。三方生态被切断。
3. **注册即同意**：每个新包首次注册弹一次"允许 X 应用作为 Agent 连接"，并记住决定；权限变成普通权限。

**建议**：1 + 3 的组合——保留权限，但把"注册"也做成一次显式的用户确认（通知里显示包名+签名指纹），并在设置里可撤销。
**理由**：权限只解决"能不能 bind"，不解决"用户是否知道谁连进来了"；撤销入口目前没有。
**不决定的后果**：恶意应用可以用户已授权的前提下持续注册、写任务、刷审批通知（当前 audit 的 P0-4 只修了入口，没修"可见/可撤销"）。

### 🔴 A2. 同步通道是否需要 Keystore P-256 绑定

**问题**：`sync_seed` 是明文 SharedPreferences 里的 Ed25519 种子；P-256 签名只存在于测试 Activity。复制该种子即可冒充本机。

**选项**
1. 用 Keystore P-256 对绑定 transcript 签名，对端用配对记录中的指纹验证（需要双方都升级）。
2. 用 Keystore 包裹种子（种子不再明文，但导出/备份仍可能带走）。
3. 接受现状，文档写明"种子等同于身份，泄露即冒充"。

**建议**：2 先做（成本低、立即消除明文种子），1 作为跨设备同步正式化时的前置条件。
**不决定的后果**：任何能读 app 私有目录的人（root、取证镜像、被攻陷的备份）都能冒充本机与已配对设备通信。

### 🔴 A3. 锚点威胁模型：要防到哪一层

**问题**：锚点状态（count+head）现在存在 DB 之外的 SharedPreferences，用设备密钥 MAC 保护。但它在同一个 app 数据目录里——**能改 DB 的攻击者如果也能改偏好文件，仍可删掉状态文件触发一次性重建**。

**选项**
1. 明确威胁模型为"只改 DB 文件"（root 改 DB 但不动偏好）——当前实现即满足。
2. 再加一层：状态文件与 DB 放在不同存储域（如 SAF 外部目录），或绑到设备级 attestation。
3. 接受一次性重建是已知降级，但在页面显示"基线重建过"的永久标记。

**建议**：1 + 3：文档写清边界，审计页对"重建过"给出持续的可见标记（而不是一次性 toast）。
**不决定的后果**：用户以为"有设备密钥就防篡改"，实际只在特定攻击模型下成立——这正是原 audit 里最危险的一条的残留部分。

### 🟡 A4. 配对码：要不要用户读码

**问题**：`confirm(..., code, code)` 自己比自己，码由两个公开指纹派生；码还写进 logcat。

**选项**
1. 要求用户输入对端屏幕上的 6 位码（标准 SAS），常量时间比较。
2. 只显示双方码，让用户肉眼比对（当前行为）。
3. 去掉纯指纹配对，只保留 Rust 路径的绑定式 SAS。

**建议**：1。删除配对码日志是配套的必做项。
**不决定的后果**：中间人可以同时和两边配对而用户无感；logcat 泄露配对码后连肉眼比对都失效。

### 🟡 A5. 日志与屏幕文本的敏感面

**问题**：配对码、无障碍读到的节点文本仍在 logcat；崩溃原文未清洗就进诊断导出。

**选项**
1. 一律不打印（推荐）：配对码/节点文本/崩溃 message 只记哈希或类型。
2. 仅 `debug` 构建打印。
3. 保留并文档说明"logcat 视为敏感"。

**建议**：1；诊断导出的 `note` 从"保证不含内容"改为"尽力而为 + 用户自行检查"。
**不决定的后果**：用户被引导分享诊断时，可能把任务文本、屏幕内容带出去。

## B. 数据生命周期

### 🔴 B1. 审计只增不减 vs 导出上限

**问题**：P0-1 之后删任务不再删审计行，审计**永久增长**；档案导出上限是 32 MiB / 20000 条。长期使用后导出会永久失败。

**选项**
1. **保留全量**，导出改为流式/分片（迁移负担在格式上）。
2. **滚动窗口**：只保留最近 N 条（如 20 万）或最近 12 个月，裁掉的部分改用"分段锚定摘要"（每段一个 MAC 的 Merkle 根）。
3. **按任务归档**：任务结束时把其审计行压缩成一条"任务摘要"事件，全量历史放进可选导出。

**建议**：3（对用户最直观，体积可控）+ 导出流式化。
**不决定的后果**：重度用户某天再也导不出档案，或者被迫容忍导出失败——而导出是唯一的数据迁移路径。

### 🟡 B2. 导入的审计事件要不要标来源

**问题**：从别人的档案导入的审计事件与本地事件外观完全相同，可以伪造「capability_granted」「task_succeeded」。

**选项**
1. 加 `origin` 字段（`local` / `imported:<fingerprint>`），审计页显示来源，导出保留。
2. 导入事件单独表，不进入本地链。
3. 现状（无标记）。

**建议**：1，并在审计页对 imported 事件加视觉区分。
**不决定的后果**：朋友给的档案可以往你的历史里塞伪造的成功/授权记录。

### 🟡 B3. 记忆要不要保留历史版本

**问题**：现在每个记忆只保留"当前版本 + 冲突候选"，编辑前的版本不保留（同步需要的历史由候选承担）。

**选项**
1. 现状：只留当前版本。
2. 保留最近 K 个版本（本地历史），同步仍只发当前版本。
3. 完整版本历史（CRDT 风格）。

**建议**：2（K=5），作为"误编辑可回滚"的最小可用能力。
**不决定的后果**：用户改错内容无法回滚，只能靠档案里的旧副本。

### 🟡 B4. 换机迁移只支持档案

**问题**：`dataExtractionRules` 排除了 DB/偏好/文件（因为 Keystore 密钥不迁移）。换机只能靠 `.taos` 档案。

**选项**
1. 接受（文档+引导流程：首次启动/设置里提示"换机请用加密导出/导入"）。
2. 增加"设备间直传"：旧机导出、新机扫码导入的一次性流程。
3. 允许备份但加密钥包裹（需要处理密钥迁移，复杂且脆弱）。

**建议**：1 立即做引导，2 作为后续功能。
**不决定的后果**：用户换机后直接重装，得到空库并以为"数据丢了"。

## C. 同步协议

### 🟡 C1. 向量时钟用墙钟

**问题**：`clock.put(localActor(), System.currentTimeMillis())`——时间回拨或同毫秒两次编辑会让合并判断错误。

**选项**
1. 混合逻辑时钟（HLC）：物理时间 + 逻辑计数器，单字段排序。
2. Lamport 计数 + 设备 id，完全放弃物理时间。
3. 现状并文档说明。

**建议**：1（可读性好，兼容现有 `actor:time` 编码）。
**不决定的后果**：手机时间被 NTP 校正或用户手动调整时，可能出现"旧内容覆盖新内容"。

### 🔴 C2. 双密钥回退语义："解不开"≠"不存在"

**问题**：vault 可用时走 Rust 封装，失败时静默回退 Keystore；导出时解不开的行被跳过。用户看到的是"记忆消失"，而不是"解不开"。

**选项**
1. 失败即报错（fail closed），列表显示"该设备无法解密 N 条记录"并提供修复/重置入口。
2. 现状：静默回退/跳过。
3. 双写：两条路径都存，任一可解。

**建议**：1（P1 已经加了计数与重置入口，缺的是**默认把它显示出来**而不是只在设置深处）。
**不决定的后果**：密钥丢失或迁移后，用户以为数据被删了，可能继续用空库覆盖关键状态。

### 🟡 C3. 多设备并发编辑

**问题**：目前只验证过"同机双包"，没有真正多设备并发。

**选项**
1. 明确"单写者"假设：同一时间只有一台设备编辑，冲突靠墓碑优先。
2. 实现合并提示 UI（发现冲突时让用户选）。
3. 完整 CRDT。

**建议**：1，并在 UI 明示"同步是手动、单写者"。
**不决定的后果**：两台设备同时编辑会静默丢一侧的修改。

## D. 发布与密钥

### 🔴 D1. 生产签名与密钥托管

**问题**：所有版本都是开发密钥（`9effee32…`）签名；离线备份在个人目录；季度演练靠人工。

**选项**
1. 继续开发密钥侧载，明确"不是生产分发"。
2. 申请 Play 商店，使用 Play App Signing（Google 托管密钥）。
3. 自建 CA/HSM，做真正的发布签名分割。

**建议**：短期 1（诚实标注已做），长期 2 或 3 二选一——这决定"这项目是否要面向普通用户分发"。
**不决定的后果**：用户无法判断"这是不是能长期用的应用"；密钥丢失/泄露没有恢复路径。

### 🟡 D2. schema 升级不可回退

**问题**：`DATABASE_VERSION = 13`，`onDowngrade` 直接抛异常。装回旧版应用会崩溃。

**选项**
1. 接受（提示"请勿降级"）。
2. 提供导出→重装→导入的降级路径文档。
3. 做兼容层（成本高）。

**建议**：2，写进发布说明与首次启动提示。
**不决定的后果**：用户回滚版本后应用无法启动，只能清数据。

## 建议的处理顺序

1. **A2 + A4 + A5**（种子保护、配对码校验、日志清洗）——安全收益最高、互不耦合；
2. **C2 + B4**（解不开就显示、换机引导）——直接影响用户是否丢数据；
3. **B1 + B2**（审计保留策略与来源标记）——决定长期可用性与可信度；
4. **A1 + A3**（Agent 撤销入口、锚点威胁模型写清）——产品承诺层面；
5. **C1 + C3 + D1 + D2**——协议与分发层面的中长期决策。
