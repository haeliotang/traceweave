# 系统级能力清点（缺口 8）

状态：清点与判断，未新增实现。目的：说清“与系统 UI、权限、分发的整合”现在到哪一步。

## 1. 已有并验证

| 能力 | 实现 | 验证 | 限制 |
|---|---|---|---|
| 通知 | `NotificationChannel` + 权限申请 | 设备：通知权限状态可见 | 无通知内容分级 |
| 系统分享接收 | `ACTION_SEND` + 选择器矩阵 | 设备：分享进入应用 | 只接受文本 |
| 文件选择/保存 | `ACTION_OPEN_DOCUMENT` / `ACTION_CREATE_DOCUMENT` | 设备：档案导入导出、审计导出 | 依赖系统文件选择器 |
| 悬浮胶囊 | `TYPE_APPLICATION_OVERLAY` | 设备：可见、可拖 | 需用户手动授予悬浮窗权限 |
| 无障碍服务（实验） | `AccessibilityService` 破障定位 | 设备：服务可启用 | 未做商店合规评估 |
| 外设 | BLE 指环、物理按键（实验） | 部分 | 未做长期稳定性 |
| Provider / Broker | 签名级 `ContentProvider` + 能力白名单 | 隔离验证 | 只对签名匹配的调用方开放 |
| 后台任务 | `JobScheduler` 周期同步 | 设备：任务注册/取消 | 真实同步需第二台设备 |

## 2. 明确没有

| 能力 | 现状 | 为什么难 |
|---|---|---|
| 默认助手 / 语音入口 | 无 | 需要 `VoiceInteractionService`、系统级角色申请 |
| 通知监听、短信、通话读取 | 无 | 高敏感权限，与数据主权目标冲突，除非逐条用户授权 |
| 全局悬浮工具条常驻 | 仅悬浮胶囊 | 厂商限制与耗电 |
| 开机自启 | 无 | 需要 `RECEIVE_BOOT_COMPLETED`，当前未声明 |
| 系统级快捷方式 / 分享目标 | 有分享接收 | 未声明快捷方式（Shortcuts） |
| 多用户 / 工作资料隔离 | 未验证 | 需要设备与策略 |
| 应用商店分发 | 无 | 需签名托管与政策评估（缺口 6） |

## 3. 与终极目标的距离

终极目标里的“系统级落地”不等于“拿到更多权限”，而是：

1. **可发现**：用户能从系统入口（分享、助手、快捷方式）找到它；
2. **可信任**：每次能力使用有明确授权与审计；
3. **可维护**：分发与更新通道可靠。

当前 1 部分具备（分享、通知），2 具备（逐次授权 + 审计），3 缺失（缺口 6）。

## 4. 建议顺序

1.  shortcuts（`ShortcutManager` 静态快捷方式）：零权限、可见收益；
2. 开机自启：只用于恢复定时同步，需与缺口 4 的调度一起评估耗电；
3. 默认助手入口：需要系统角色，收益大但风险与合规成本高，放在独立审计之后；
4. 通知监听类：除非有明确用户场景，否则不做。

## 5. 本轮结论

- 不解锁新权限；
- 唯一确定要做的小项是 **静态快捷方式**（零权限、可验证）；
- 其余系统能力等独立审计与分发决策之后再说。
