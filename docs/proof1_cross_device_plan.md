# Proof 1 — Cross-device Memory Continuity & Sync Trust（执行计划）

目标：证明同一用户的**记忆**能在两台物理设备之间可信地同步（含编辑、删除、断网恢复、重启与撤销），
并在撤销配对后拒绝重连。

**本 Proof 的范围**（2026-11-07 收窄）：只覆盖记忆记录、版本与删除墓碑，以及同步信任链。
任务、授权记录与完整审计历史的跨设备迁移是**独立的证明**，不在本计划内，不能用本文的 7 个步骤
宣布"整个设备无关目标通过"。

状态：**未开始 —— 需要第二台物理 Android 设备**。本文把步骤、观测点和判据写死，避免有设备时临场设计。

## 0. 前置条件

| 项 | 要求 |
|---|---|
| 设备 | 两台**不同物理设备**（模拟器不算；同机双包已完成，不能替代） |
| 版本 | 两台都装 **0.1.5**（同一签名 `9effee32…`，`adb install -r` 覆盖升级已验证）。0.1.5 起同步载荷带 P-256 通道绑定，**≤0.1.4 的对端会被 `not_bound` 拒绝**，混装版本会表现为"同步失败"而不是产品缺陷 |
| 网络 | 同一局域网；服务端监听 `/ip4/0.0.0.0/tcp/47960`，拨号优先使用配对时保存的 `/ip4/<对端>/tcp/47960`。局域网发现依赖 mDNS/组播（应用会申请 `CHANGE_WIFI_MULTICAST_STATE`），若网络屏蔽组播则使用配对卡里的地址握手 |
| 数据 | 设备 A 至少 2 条记忆、1 个任务；设备 B 为空库（或先导出备份后重置） |
| 记录 | 每一步产出 JSON 收据，放在 `artifacts/agent_os/next_stage/proof1_<date>/` |

## 1. 验收步骤（每步都有可观测判据）

| # | 操作 | 判据 |
|---|---|---|
| 1 | A：设置 → 配对设备，显示本机指纹与 6 位码；B 同样操作并输入 A 的码；A 输入 B 的码 | 双方提示配对完成；`已配对设备：1`；`管理设备` 列表出现对端 deviceId 与指纹前缀 |
| 2 | A：设置 → 同步现在（对端等待时 B 也点等待/同步） | 双方 `后台同步上次结果` 显示 applied>0（A→B 首轮为导入条数）；B 记忆库出现 A 的记忆 |
| 3 | B：编辑其中一条记忆内容并保存 | B 详情显示「用户已修正」；A 执行同步后，A 上该记忆内容变为 B 的值（不再被旧内容回滚） |
| 4 | B：删除该记忆 | B 记忆库不再显示；A 同步后该记忆消失（墓碑传播）；A 审计页出现 `task_deleted`/`memory` 相关事件且「防篡改校验」仍为绿 |
| 5 | 断网：双方关闭 Wi-Fi，A 新建一条记忆并编辑；恢复网络后双方各同步一次 | 断网期间的本地变更在恢复后合并且不丢；两库内容一致 |
| 6 | 双方强制停止应用并重启，再同步一次 | 配对关系、游标、记忆与审计链在重启后仍有效；A/B 审计页均显示链完整；**同步成功后对端地址仍是 LAN 地址，不会被写成 127.0.0.1** |
| 6b | **已建立链条后的丢响应**：在 B 已接受请求之后、A 收到响应之前断网（或强制停止 A） | A 重试时 B 以恢复模式接受旧 challenge 并重发当前 challenge；A 最终同步成功；副作用不重复（记忆条数/版本数不翻倍）；不允许出现只能删除配对才能恢复的死锁 |
| 6b-1 | **首次同步的丢响应**（挑战链尚未建立）：A 第一次请求发出、B 已接受并写库后，丢弃 B 的响应 | 重试仍携带全零 challenge；B 以恢复模式接受并重发 C1；A 同步成功且数据不重复。首次与"已建立链条"的丢响应必须分别测，不能互相替代 |
| 6c | 双方向各重复一次 6b（两个方向都丢响应） | 同样收敛；审计里没有 `challenge_mismatch` 导致的永久失败 |
| 7 | B：管理设备 → 撤销 A 的配对；A 再尝试同步 | B 不再接受 A 的会话（A 侧报错/无 applied）；B 的已配对设备归零 |

## 2. 观测与证据采集

- 结构：`adb -s <serial> shell dumpsys activity services`（确认同步服务运行）、`logcat`（只取 `Traceweave|AgentOs` 标签，**不要**抓屏文本）。
- 应用内：设置页的「后台同步上次结果」、记忆库、任务详情、审计页「防篡改校验」行。
- 截图：配对码界面（打码）、同步结果、审计页、B 的记忆库。
- 每步写 `step<N>.json`：时间、A/B serial、操作、可见结果、失败时的 logcat 片段（脱敏）。

## 3. 判据（全部满足才算 Proof 1 通过）

1. 步骤 1–7 全部通过，且第 5、6 步不丢数据。
2. 两台设备的审计页在最后一步仍显示「链完整 + 锚定」。
3. 撤销后重新配对不再自动恢复信任（需要重新走 6 位码）。
4. 收据里没有任何真实的个人内容（只允许结构性统计与合成数据）。

## 3.5 证据边界（宿主测试不等于本计划）

宿主测试（`test_transport_binding`、`test_challenge_chain`）验证的是信封解析/签名规则与挑战
状态机的纯逻辑，**没有**重启 Android 进程、重开 SQLite、或调用 `SyncRecords.merge` 统计条数。
因此它们能支持"恢复规则成立"，**不能**支持"真实重启后无重复副作用"——后者只能由本计划的
6b/6b-1 步骤在真机上给出收据。

## 4. 已知限制（写进收据，不当作失败）

- **单写者假设**：两台同时编辑同一条记忆的合并结果未定义，Proof 1 只验证"交替编辑"。
- **同步种子可导出**：种子自 0.1.4 起用 Keystore 包裹，0.1.5 起载荷带 P-256 通道绑定（复制种子不再能同步）；配对阶段通过 SAS 或带外配对卡认证指纹。
- **配对认证**：码配对用 Rust SAS（绑定双方 P-256 指纹 + 传输公钥），手工路径用带外配对卡 + 显式确认。仍未覆盖剪贴板等传递通道的泄露。
- **后台可达性**：周期任务只在系统允许时运行；跨设备无人值守同步不在 Proof 1 范围内。

## 5. 后续（Proof 1 通过之后）

1. **跨会话重放**：签名时间戳、挑战链、ack 与恢复模式（0.1.5 已实现，见 `sync_protocol_design.md` §14）；还需要一次真实的断网重放尝试来确认行为。
2. **冲突 UI**：真正的双设备并发编辑需要可见的合并/选择界面，而不是依赖单写者假设。
3. **第三方 Agent 注册确认门**：当前是"权限 + 连接通知 + 撤销"，若要做逐次确认需改 SDK 协议。
4. **任务、授权与审计历史的跨设备迁移**：SyncRecords 只交换记忆记录、版本与墓碑；任务/授权/审计需要独立设计与独立 Proof。

## 6. 需要用户提供

- 第二台设备的 `adb serial`（`adb devices` 可见），以及它是否已装过本应用。
- 两台设备是否允许在同一 Wi-Fi 下互相发现（部分企业/访客网络屏蔽组播）。
