# 跨设备同步协议设计（C1 草稿）

状态：**已批准（2026-10-30），C2 已实现传输骨架**。本文件定义 Agent OS 记忆与任务跨设备同步的身份、配对、传输、合并、删除、回执与恢复语义，是 C2–C6 的实现依据。评审通过前不写生产同步代码。

关联：[里程碑](agent_os_milestones_2026-10-30.md)、[后续开发记录](agent_os_next_stage_2026-10-27.md)、[记忆与工作流边界](agent_os_context_memory_workflows.md)。

## 1. 目标与非目标

目标：两台或多台由同一用户持有的设备，在不依赖可信服务器的前提下交换记忆、任务与删除意图；用户对冲突和删除有最终控制权；任何一步失败都可重试且不会重复产生副作用。

非目标（本轮不做）：共享给其他用户、群组协作、服务端明文处理、后台常驻自动同步、跨账号迁移、网页端。

## 2. 现有可复用件与差距

| 能力 | 现状 | 差距 |
|---|---|---|
| 设备身份 | [DeviceIdentity.java](../agent_os/android/src/com/inceptless/traceweave/DeviceIdentity.java) 生成 Keystore P-256、签名与指纹 | 未被任何用户流程调用 |
| 传输 | Rust libp2p/Noise 实验（`agent_os/tests/libp2p_live_binding`） | 未进正式模块，密钥是公开测试夹具 |
| 因果合并 | [causal_memory.rs](../agent_os/core/src/causal_memory.rs) 纯函数 + SQLite 夹具 | 未接 Android 规范记忆库与持久化 |
| 回执 | SQLite 合成夹具 | 未与合并代码连接，清理策略未定 |
| 删除优先 | 档案导入已实现墓碑优先与逐条审核 | 只覆盖手动档案，不是增量同步 |
| 传输上限 | 10 MiB 档案/字段限制 | 需要按记录批次重新定义 |

## 3. 威胁模型

**资产**：记忆内容、任务与审计历史、删除意图、设备身份与配对关系、恢复材料。

**对手**：
1. 网络攻击者：中间人、重放、篡改、拒绝服务。
2. 恶意或被攻陷的已配对设备：伪造记录、复活已删内容、滥发数据。
3. 丢失或被盗设备：离线后重入。
4. 不可信中继：只应看到密文与最少元数据。
5. 本地恶意应用：无 root，不能读应用私有目录。

**假设**：Android Keystore 私钥不可导出；用户会核对配对码；设备未 root；系统未被打补丁绕过。

**明确不防**：root/物理芯片提取、供应链投毒、流量分析（仅做最小化，不做匿名化）。

## 4. 设备身份

- 每个安装生成一次 P-256 签名密钥（Keystore，不可导出），以及一个随机 `device_id`（128 位）。
- `device_fingerprint = SHA-256(SPKI)`，界面显示为分组十六进制，供用户核对。
- 传输层使用独立的 Ed25519 PeerId（libp2p Noise 要求传输密钥参与握手）。Keystore 密钥不替代 PeerId，而是**绑定**它：

```
binding = Sign_keystore("traceform-sync-v1" || peer_id || device_id || nonce)
```

绑定记录随配对保存；接收方用实际握手得到的 PeerId 与配对记录比对，绑定失败即拒绝。

- 私钥缺失时**不自动重建身份**：应用进入“身份缺失”状态，要求用户重新配对或恢复。

## 5. 配对流程

1. 设备 A 打开“添加设备”，显示二维码：`{device_id, peer_id, fingerprint, token, expires_at}`，token 一次性、5 分钟有效。
2. 设备 B 扫码，建立连接，双方分别用 Keystore 对包含双方 PeerId、临时密钥与 token 的转录哈希签名。
3. 双方各自显示同源的 6 位确认码（由转录哈希派生），用户在两台设备上确认。
4. 任一步失败、超时或确认码不一致 → 丢弃配对，不写入任何信任。

配对记录：`{peer_device_id, peer_fingerprint, peer_id, paired_at, status}`。拒绝路径必须覆盖：未知设备、token 过期、token 重放、指纹不匹配、确认码不一致。

## 6. 会话与传输

- Noise XX 握手；握手完成后交换 Keystore 绑定签名，验证通过才允许发数据。
- 每次连接有独立 `session_id`（随机 128 位）与递增记录序号；接收方维护有限窗口（如最近 256 个 session_id）拒绝重用。
- 单条记录上限 1 MiB，单批上限 8 MiB，单会话记录数上限 10,000；超限即断开并记录。
- 传输不依赖系统 TLS；Noise 提供机密性与完整性。中继（若引入）只能看到密文与连接元数据。

## 7. 数据模型

记录类型：`memory`、`task`、`tombstone`、`sync_receipt`。

```
record = {
  record_id,        // 与本地 ID 相同
  type,
  version: {hlc_wall_ms, hlc_counter, device_id},
  content_hash,     // SHA-256(payload)
  payload           // 仅业务字段
}
```

- 版本使用混合逻辑时钟：物理毫秒 + 计数器，`device_id` 兜底；比较规则：因果可判定时按因果，否则视为并发。
- `content_hash` 用于去重与完整性校验，不可省略。
- 合并后的时钟设备数上限 32（延续现有规则），超限拒绝合并并提示用户。

## 8. 冲突与删除

- 并发编辑：**不自动覆盖**。两条都保留为候选，用户在“记忆冲突”界面逐条选择；选择后写入带合并时钟的解决记录。
- 删除：墓碑版本优先于任何并发编辑与旧版本；导入/同步不得复活已删记录。
- 墓碑保留：至少 180 天，且必须等所有已配对设备确认收到；提前清理需要用户显式确认并记录原因。
- 与删除并发的编辑按现有规则丢弃；若产品要保留，需另设“恢复已删内容”流程，不能绕开删除优先。

## 9. 回执与幂等

- `operation_id = SHA-256(record_id || version || content_hash)`。
- 接收方在同一事务内写入业务变更与回执；重复 operation_id 直接返回上次结果。
- 同一设备复用 operation_id 但内容哈希不同 → 拒绝并记录审计。
- 崩溃/断网后按 manifest 差异重传；manifest 只含 `{record_id, version, content_hash}`，不含内容。

## 10. 授权边界

同步只复制记录与墓碑，**绝不**复制：文件 URI 与持久授权、能力授予、云 API Key、云端同意标记、通知/日历权限。

接收方执行外部动作仍需本机用户逐次确认；同步完成不等于获得任何权限。

## 11. 密钥恢复与撤销

- Keystore 私钥不可导出，因此“恢复”是指：用离线保存的恢复材料在新设备上重建身份并重新获得旧设备信任，而不是导出旧私钥。
- 恢复材料：用户持有口令加密的恢复文件，内含恢复密钥对与设备标签；丢失口令即不可恢复，丢失 Keystore 后旧设备上的加密数据也不能替代档案。
- 新设备恢复：新 Keystore 身份 + 恢复文件 → 旧设备确认（或双设备配对）→ 写入新配对记录，旧记录标记 `rotated`。
- 撤销：删除配对记录并广播签名的撤销记录；对端收到后立即断开、拒绝重连、丢弃未完成会话。
- 旧设备重入：撤销后重连必须重新完整配对，不能凭旧绑定或旧回执恢复信任。

## 12. 失败模式

| 场景 | 期望行为 |
|---|---|
| 提交前崩溃 | 事务回滚，无回执，可重试 |
| 提交后、回复前崩溃 | 回执已存，重试返回重复确认，不重复应用 |
| 断网/超时 | 会话作废，按 manifest 差异续传 |
| 时钟偏差 | 因果合并优先；无法判定时保留候选交用户 |
| 重复投递 | operation_id 去重 |
| 撤销与在途会话竞争 | 撤销记录版本更高，接收方关闭会话并丢弃后续帧 |
| 墓碑被旧备份重放 | 墓碑优先，旧记录不复活 |

## 13. 实现阶段与验收判据

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| C2 | Noise/libp2p 进正式模块；Keystore 绑定签名接入握手 | 宿主测试 + 两进程互通；绑定失败被拒；默认关闭 |
| C3 | 配对 UI 与双身份 | 双设备（或同机两 UID）配对成功；确认码不一致拒绝；重启后保持 |
| C4 | 撤销、轮换、旧设备重入 | 撤销即时断开；轮换后旧绑定失效；旧设备重入被拒 |
| C5 | 因果合并接入 AgentStore 事务 | 并发编辑、删除优先、重放、32 设备上限测试通过 |
| C6 | 端到端同步 | 断网重试、冲突选择、删除传播、恢复四类场景通过；可重复脚本 |

每一阶段都必须保留“默认关闭”的开关，用户显式开启后才建立连接。

## 14. 未决问题（需要用户决策）

1. 第一版是否需要中继服务器？仅局域网/热点直连可以显著降低隐私与运维面。
2. 墓碑保留期 180 天是否合适？更短会提高旧备份复活风险。
3. 传输实现走 Rust JNI 还是 Kotlin 重写？JNI 复用现有实验，但增加原生崩溃面。
4. 恢复文件的口令强度与备份位置如何约束？
5. 同机多用户/工作资料是否需要支持？

## 15. 明确不做

- 不做自动后台同步（第一版只能用户手动发起）。
- 不做服务端明文存储、不做服务端搜索。
- 不把同步当作权限授予。
- 不承诺物理擦除：已同步到对端的副本只能通过对端删除协议处理。
