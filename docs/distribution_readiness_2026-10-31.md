## 2. 必须先决定的三件事

### 2.1 签名身份归谁

- **现状**：密钥在开发机 Keychain 里，口令通过环境变量注入。
- **风险**：密钥丢失 = 无法升级已安装用户；密钥泄露 = 可冒充发布。
- **需要你决定**：是否生成独立“发布密钥”，并把恢复副本保存在离线介质（例如两个物理位置）。

### 2.2 分发渠道

| 选项 | 优点 | 代价 |
|---|---|---|
| GitHub Releases + 侧载说明 | 零审核、当天可发 | 用户需允许“未知来源”；无自动更新 |
| Google Play 内部测试轨 | 自动更新、可回滚 | 需开发者账号与政策审核；无障碍/悬浮窗服务需申报 |
| F-Droid | 开源友好 | 审核周期长；需可复现构建 |
| 自建更新源 | 完全可控 | 需自己实现更新校验与签名链 |

**建议**：先 GitHub Releases（配合本仓库已有的发布校验），把 Play 作为第二步。

### 2.3 更新与降级策略

- 同签名才能覆盖安装；降级需要 `versionCode` 更低且用户手动允许；
- 数据库 schema 只升不降：**新版写过的库不能被旧版打开**（当前 `onUpgrade` 没有降级路径）；
- 需要在发布说明里写明“升级后不可回退到 0.6.x 之前的版本”。

## 3. 发布前检查清单（本地可执行）

1. `prepare_release_android.py --require-model-runtime --require-sync-runtime` 通过；
2. `verify_release_android.py` 输出签名与包内容校验通过；
3. `acceptance_android.py` 通过（当前 0.6.14 已有收据）；
4. 宿主测试全绿（含 `test_string_keys`、`test_grammar_runtime`、`test_structured_repair`）；
5. 设备冒烟：主屏、任务、记忆、同步、审计各开一次；
6. 发布说明写明：数据格式版本、已知限制（跨设备未验证、模型 token 上限）。
