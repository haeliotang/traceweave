## 2. 风险

1. **身份来源**：两套证书都产生于开发阶段，审计历史里存在可调试版本；即使现在构建非调试包，证书本身没有"生产"含义。
2. **单点持有**：私钥在本机、口令在钥匙串、备份在用户处。电脑与恢复密钥同时丢失即失去更新能力（用户已确认另存恢复密钥）。
3. **切换成本**：Android 更新要求签名一致。换密钥意味着**不能覆盖安装**，只能卸载重装（丢数据）或换包名/换分发渠道。
4. **无商店背书**：侧载没有 Play App Signing 之类的密钥托管与恢复机制。

## 3. 选项

### A. 继续使用现有密钥（默认）

- 优点：零迁移成本，历史安装可继续覆盖升级。
- 缺点：证书没有生产含义；一旦泄露，攻击者可发布"同签名"更新；无密钥轮换路径。

### B. 新生产密钥 + 包名不变

- 需要：卸载重装，用户数据必须先用加密档案导出再导入；旧安装无法收到新签名更新。
- 优点：干净的生产身份，可与开发密钥分离。
- 缺点：一次性的数据迁移与安装中断；若用户设备上还有未导出数据，风险由用户承担。

### C. 新生产密钥 + 新包名（并行）

- 需要：新包名、新应用条目，旧包保留为"开发版"。
- 优点：不破坏现有安装；可在新包上做签名托管与商店分发。
- 缺点：两套并存，同步/导入需要在包间迁移；用户要重新授权权限。

## 4. 建议

在**没有商店分发**的当前阶段：继续使用现有密钥（选项 A），但把以下约束写死：

1. 私钥只存在于受控目录与用户持有的加密归档；仓库、聊天、日志不得出现；
2. 每次发布前核验签名证书与上一版一致（已有检查）；
3. 不把"能签名"当作"可信"：发布说明必须标注"开发密钥侧载"；
4. 一旦决定进入商店或对外分发，切换到**选项 C**（新包名 + 新密钥 + 商店密钥托管），旧包冻结为开发版，并在迁移文档里写明档案导出/导入步骤与权限重授权清单。

不建议选项 B：代价（卸载丢数据）与收益（证书含义）在侧载场景下不匹配。
